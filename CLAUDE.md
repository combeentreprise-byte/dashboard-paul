## What this is

Revenue Dashboard: a Next.js app that displays invoice/revenue stats sourced from Everbill (v1), with
Odoo and Google Drive planned as future sync sources. A scheduled job writes into Supabase Postgres via
Prisma; the dashboard itself only ever *reads* from that database — it never calls Everbill directly.

## Commands

- `npm run dev` — start the dev server (http://localhost:3000)
- `npm run build` / `npm run start` — production build / start
- `npm run lint` — ESLint (flat config, `eslint.config.mjs`, extends `next/core-web-vitals` + `next/typescript`)
- `npx prisma migrate dev --name <name>` — create/apply a migration after editing `prisma/schema.prisma`
- `npx prisma generate` — regenerate the Prisma client (needed after pulling schema changes)

There is no test runner configured in this repo.

### Triggering a sync locally

```bash
curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/sync/everbill
```

`CRON_SECRET` must match the value in `.env`. In production, Vercel Cron calls this same route on the
schedule defined in `vercel.json` and sends the header automatically.

## Architecture

**One-way data flow, no client-side fetching to external services:**

```
Everbill API --(sync job)--> Supabase Postgres (via Prisma) --(Server Component reads)--> Dashboard UI
```

- `app/api/sync/everbill/route.ts` — the only place Everbill is called. Auth-gated by comparing the
  `Authorization: Bearer` header against `CRON_SECRET`. Calls `syncEverbillInvoices()` and returns JSON.
- `lib/everbill/client.ts` — thin REST wrapper (`fetchAllInvoices`, paginated). **Endpoint paths, auth
  header format, and field names are provisional** — not yet checked against real Everbill docs/credentials.
  This is the sole file to adjust once real API details are known; everything downstream is written
  against the `EverbillInvoice` type it exports.
- `lib/everbill/sync.ts` — maps `EverbillInvoice` → the `Invoice` Prisma model and upserts by
  `everbillId`. `mapStatus()` is a similarly provisional string→enum mapping; unrecognized statuses fall
  back to `OPEN` rather than throwing, so one bad record doesn't fail the whole sync.
- `prisma/schema.prisma` — single `Invoice` model (`InvoiceStatus` enum: DRAFT/OPEN/PAID/OVERDUE/CANCELLED).
  `raw` (Json) keeps the original Everbill payload alongside the mapped fields.
- `lib/db/stats.ts` — all read-side query helpers (`getTotals`, `getMonthlyRevenue`, `getTopCustomers`,
  `getStatusBreakdown`, `getLastSyncedAt`). The dashboard page composes these; add new aggregations here,
  not in the page component.
- `app/page.tsx` — the dashboard, a Server Component that awaits all `lib/db/stats.ts` queries in
  parallel and renders empty-state UI when no invoices have synced yet.
- `components/charts/*` — Recharts-based chart components, one per visualization, each taking the
  shaped data from a `lib/db/stats.ts` return type as props.
- `lib/db/prisma.ts` — standard Next.js dev-mode Prisma client singleton (avoids exhausting connections
  via hot reload).

**Two Postgres connection strings** (both point at the same Supabase project, see `.env.example`):
`DATABASE_URL` is the pooled/PgBouncer connection used at runtime; `DIRECT_URL` is the direct connection
Prisma Migrate needs (PgBouncer's transaction pooling doesn't support prepared statements).

**Styling**: Tailwind v4 (`@import "tailwindcss"` in `app/globals.css`, no separate config file) plus a
custom CSS-variable design system for colors (`--surface-1`, `--text-primary`, `--series-1..4`,
`--status-*`, etc.), with dark mode via `prefers-color-scheme`. Components reference these vars directly
via inline `style={{ color: "var(--text-primary)" }}` rather than Tailwind color utilities — follow that
convention for new UI rather than hardcoding colors or adding Tailwind color classes.

## Important notes

- **This is not the Next.js you know.** Per `AGENTS.md`, this project pins a Next.js version with
  breaking API/convention changes from training data. Before writing Next.js code, read the relevant
  guide under `node_modules/next/dist/docs/`. That `AGENTS.md` block is regenerated by `next dev` — don't
  remove it from diffs, and commit it as-is if it reappears.
- Everbill field mappings (`lib/everbill/client.ts`, `lib/everbill/sync.ts`) are best-effort guesses and
  will likely need real correction once actual API docs/credentials are available — treat values there as
  provisional, not verified contract.
- No authentication currently exists on the dashboard UI itself, only on the sync endpoint. Don't add
  auth or other unrequested features without confirming with the user first.
